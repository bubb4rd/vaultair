# Security assumptions

> **Status:** Phase 3 first version. Updated in Phase 5 (OS integrations, clipboard), Phase 7 (accounts) and Phase 15b (Windows Hello unlock), and reviewed against the implementation in Phase 16 (2026-10-06). The threat model (`docs/threat-model.md`) says what Vaultair defends against; this document lists what that defense *relies on* and where its limits are.

## Libraries we trust

| Component | Used for | Why it's trusted |
|---|---|---|
| RustCrypto `argon2` 0.6 | Master password KDF | Widely used, pure Rust, zeroizes its memory (`zeroize` feature enabled) |
| RustCrypto `chacha20poly1305` 0.11 | Key wrap, field envelopes | Widely used AEAD implementation |
| RustCrypto `hkdf`, `hmac`, `sha2` | Subkeys, fingerprints | Standard constructions |
| `getrandom` | All randomness | Calls the OS CSPRNG (`BCryptGenRandom` on Windows) |
| SQLCipher 4.14.0, on SQLite 3.51.3 (bundled by `rusqlite` 0.40.2 through `libsqlite3-sys` 0.38.2) + OpenSSL 3 (vendored) | Whole-database encryption | Mature, widely deployed; settings pinned in the header |
| `zxcvbn` | Master password strength | Port of Dropbox's estimator |

Versions are pinned in `Cargo.lock`; `cargo deny` checks advisories, licenses and sources in CI.

## Assumptions

1. **The OS RNG is sound.** Salt, DEK and every nonce come from it.
2. **Random 24-byte nonces don't collide.** XChaCha20's 192-bit nonce makes this negligible at any realistic number of writes.
3. **Argon2id at ≥ 64 MiB, t=3 makes offline guessing expensive.** It doesn't make a weak password strong, which is why the policy requires 12+ characters and a zxcvbn score of 3+.
4. **The machine isn't compromised while the vault is unlocked.** See the threat model.
5. **NTFS rename is atomic.** Header writes rely on write-temp, `fsync`, rename (`MoveFileExW` with replace).
6. **Windows Hello keeps its keys and asks before using them** (only with Windows Hello unlock on). The key can't be exported, every signature needs the user's approval in a prompt Windows draws, and the same challenge always gives the same signature (RSA PKCS#1 v1.5, checked in `docs/spikes/hello-quick-unlock.md` within a process, across processes, after a restart and after a PIN change).
7. **DPAPI is tied to the Windows account**, and is trusted for nothing more: any process running as the user can undo it without a prompt. It is an outer layer on the slot, not what protects the data key.

## Known limits

- **Memory hygiene is best-effort.** Keys (`VaultKeys`, `Dek`, the KEK) and decrypted field values are wiped on drop. But copies can survive in places we don't control: Rust moves and reallocations, the SQLite page cache and SQLCipher internals (mitigated by `cipher_memory_security = ON`), the SQLCipher key literal passed through `PRAGMA key`, the IPC buffers that carry a typed password from the webview or a revealed value to it, JavaScript strings in the webview, and clipboard memory (Windows keeps copied text in a global memory block Vaultair can't wipe; clearing empties the clipboard but the freed memory isn't zeroed).
- **Secrets cross the IPC boundary as JSON strings, in both directions.**
  - *The master password, inbound:* `vault_create`, `vault_create_demo`, `vault_unlock`, `vault_change_password` (the current and the new one), `vault_strengthen_kdf`, `quick_unlock_enable`, `quick_unlock_forget`, `backup_restore_to`, `settings_update` (only to turn auto-lock off while Windows Hello unlock is on), and `strength_estimate`, which receives a new master password as it is typed (debounced) to score it. Rust moves each into a `SecretString` at once.
  - *Account secrets, inbound:* `account_create`, `account_update`, `mfa_upsert` and `mfa_set_backup_codes` carry what you typed; `clipboard_copy_plain` carries a generated password you copy before saving it. Rust wipes its own copy of each secret field when the request is dropped.
  - *Outbound:* only `secret_reveal` (one stored value), `totp_current_code` (the current code) and `generate_password` / `generate_passphrase` (a new value) return a secret. Two tests in `src-tauri/src/ipc.rs` guard this. One holds a reviewed list of every command and the type it returns (`src-tauri/ipc-surface.snap`): a new command, or a changed return type, fails until the list is updated, so it reaches a reviewer as one line. The other knows the three response types that exist to carry a value (`RevealedSecret`, `TotpCodeView`, `Generated`) and fails if a command outside the four above returns one, if another response embeds one, or if a core-only type (backup codes, keys, the header, the Hello slot) gets a TypeScript type. Neither can tell that a new *field* on an existing response holds a secret (`password: string` added to `AccountDetail` changes no line in the list), and neither reads what a plain `string` contains. For responses built from a vault's records the canary tests catch that; the responses defined in `src-tauri` (`RestoredVault`, `ClipboardCopy`, `LockNotice`, `LocationCheck`, `KdfCheck`, `AppInfo`, `IpcError`) and `SessionConfig`, `QuickUnlockStatus`, `RecentVault` and `BackupSummary` go through no canary: they hold paths, flags and settings by construction, and a change to them shows only in the `bindings.ts` diff. That still takes a reviewer.

  In every case the webview, the serializer and the IPC buffers may keep copies until their memory is reused. Rust can wipe only its own.
- **A request that fails to parse is answered by Tauri, not by Vaultair.** Its error text can quote part of what was sent. It goes back to the webview that sent it and is replaced there by the generic message. As the app is configured (no Tauri log plugin, Tauri's `tracing` feature off, no bridge from `log`), it isn't written to the log. The log plugin is kept out by not being a dependency and by `scripts/check-release-config.mjs` refusing its permissions, not by `deny.toml`, which bans network crates and the `http`, `updater`, `shell` and `fs` plugins only; that rests on reading the configuration, not on a test. It is the one error that isn't one of Vaultair's fixed strings.
- **Metadata inside the encrypted database** includes password strength scores and keyed fingerprints (Phase 7), how many backup codes are left, when each password was last changed and last shown or copied, and the sensitive-notes suggestion flags (ADR-0006: four yes/no bits per account, worked out in Rust when the notes are saved, never the text). All are encrypted at rest but readable by anything that can read the unlocked database. Fingerprints are HMACs under a vault-specific key, so they reveal nothing outside the vault; inside it they reveal which accounts share a password (which is the point of the feature).
- **Old headers and backups keep working with the old password** after a password change, because the DEK doesn't change (re-wrap only). "Rotate encryption key" is designed for but not in the MVP.
- **The CRC in the header is not a security check.** Tampering is caught by the authenticated key wrap.
- **The header reveals** that a file is a Vaultair vault, its creation time, its KDF parameters and whether it's a demo vault. It reveals nothing about contents.
- **Wrong password and tampered header are indistinguishable** by design: both are an authentication failure of the key wrap.
- **`.lock` is advisory within Vaultair.** It stops a second Vaultair instance from opening the same vault. It doesn't stop other programs from copying the (encrypted) files.
- **Timing:** a wrong password costs a full Argon2 run, like a right one. All checks before Argon2 depend only on the files, not on the password.

- **Clipboard history exclusion relies on other apps honouring it.** Windows clipboard history and cloud clipboard respect `CanIncludeInClipboardHistory` and `CanUploadToCloudClipboard`; third-party clipboard managers may ignore `ExcludeClipboardContentFromMonitorProcessing`. Any app running as you can read the clipboard while a value is on it.
- **A crash before the clear leaves the value on the clipboard.** Timed clears, "Clear now", lock and a normal exit all clear; a crash or a killed process doesn't. "Keep in clipboard" is the user opting out of the clear.
- **Idle lock can come up to 15 s late, not early.** Activity pings are throttled to one every 15 s, and activity inside that window is reported when the window ends. So Rust's record of the last activity is never earlier than the real one by the time the lock could fire (the shortest timeout is 1 minute), and can be up to 15 s later. An earlier version of this line said "early"; that describes the deadline for the few seconds before the trailing ping lands, not when the vault locks. The deadline itself is in Rust, so a stalled or compromised UI can't extend it without sending pings. Every command that reads or writes the vault counts as activity too, so a TOTP code left on screen, which fetches the next code when one expires, holds the lock off until it hides (the reveal time: 5 minutes at most).
- **Hiding a revealed value is the UI's job; locking is Rust's.** Once a value has been sent to the webview, Rust can't take it back: the hide timers and the clearing on leaving a page run in JavaScript. A lock is enforced in Rust (keys wiped, the database closed, every data command refused) whatever the webview does, but wiping what the webview already holds depends on it handling `vault://locked`, which reloads it.
- **Capture protection stops capture APIs, not people.** It hides the window from screenshot tools, screen sharing, streaming and Recall snapshots. It doesn't stop a camera, or code running with your rights that reads the window's memory. Before Windows 10 2004, captures show a black box instead of nothing. With the policy set to Custom the window is visible, lock screen included, until an account rated at or below the chosen level is open; the UI asks for that (`capture_apply`) and Rust ignores the request unless the saved policy is Custom, so the UI can't switch Always off.
- **Logs hold activity, not content.** Every log line passes fixed text plus record ids, counts, result codes or setting values: no name, username, email, web address, path or secret, so the redaction helpers in `vaultair_core::redact` have no caller today. (A panic is logged by where it happened: for Vaultair's own code a path inside the source tree, such as `src-tauri/src/lock.rs`; for a dependency the crate and file, such as `tauri-2.11.6/src/app.rs`. The compiler records a dependency's file as a full path on the PC that built the release, with that PC's user name in it; the folders in front of the crate name are cut off before logging, and any other absolute path is cut to its file name.) A log line that ever needs a username or email must go through them; the canary test fails on a raw one. A panic is logged by file and line only. Libraries' own `log` output isn't collected (no bridge is installed). Five places report a Tauri error (failing to start, to create or change the tray icon, to emit an event, to reach the webview for hardening); they log its kind, the error's variant name, and none of its text, which is Tauri's and could quote a path under your Windows profile.

- **Windows Hello unlock keeps a wrapped copy of the DEK on this PC.** Opening it takes a Hello approval; see the threat model for what that does and doesn't stop. Its rules (restart, 7 days, 3 failed attempts) are enforced by Vaultair, not by the key, and the failure count in the slot has no MAC, because nothing can be authenticated before the DEK is known. Editing the count buys more Hello prompts, never an unlock.
- **The Hello signature is key material while it is in memory.** Rust's copy is wiped after the HKDF; the WinRT buffer it arrived in can't be.
- **Restart detection is the uptime** (`GetTickCount64`), read as now minus uptime and compared within 2 minutes. Fast Startup keeps the uptime across "Shut down", and moving the system clock by more than 2 minutes reads as a restart (the safe direction).
- **TPM detection asks the TPM service** (`Tbsi_GetDeviceInfo`). Hello's own attestation reports `NotSupported` on working firmware TPMs, so it isn't used. A PC with a TPM that Hello doesn't use for some reason would not get the "no TPM" warning.

## Verified by tests

`crates/vaultair-core/tests/vault_integration.rs` covers:
- Round trip across lock/unlock.
- A wrong password runs Argon2 before failing.
- Every authenticated header field (salt, m, t, p, vault id, created-at, demo, nonce, ciphertext) is tamper-evident. A mutation test confirmed the suite fails if the AAD binding is removed.
- KDF floor and cap.
- Damaged headers; newer formats and schemas.
- Flipped database bytes; a database swapped in from another vault.
- Missing files; single-open.
- Canary scan: no plaintext in any vault file, and no secret in a plaintext SQL export (the field layer holds).
- The golden v1 fixture still opens.
- Idle lock fires exactly at the deadline, `touch` extends it, it can be turned off, and a locked session refuses data commands (`ManualClock`).

Phase 5 tests elsewhere:
- `src-tauri/src/clipboard.rs` (paused tokio clock, fake clipboard): clears after the timeout, "Keep" cancels, a later user copy is never cleared, "Clear now", a new copy restarts the timer, a busy clipboard fails cleanly.
- `src-tauri/src/lock.rs`: the ADR-0004 lock policy; a fake session-lock event locks the vault and clears the clipboard; idle and manual locks take the same path.
- `crates/vaultair-platform/src/windows/clipboard.rs` (ignored, real clipboard): the three exclusion formats are present; only our write is cleared; clearing works after the owner window is destroyed (exit).

Phase 15b tests:
- `crates/vaultair-core/src/vault/device_slot.rs`: round trip; a different signature, vault id or header is rejected; every single changed byte is caught, and edits that keep the CRC valid still fail the unwrap; a forged policy record, or one MACed with another vault's key, is refused; the data key and the signature never appear in the slot or its `Debug` output.
- `crates/vaultair-core/src/service/quick_unlock.rs` (in-memory Hello, DPAPI and uptime; `ManualClock`): unlock after one password unlock; the restart, 7-day and 3-failure rules, each without showing a Hello prompt once it applies, and each cleared by a password unlock; a changed password voids the slot, including one edited to claim the new header; a forged policy record gets past the hint and is refused after the unwrap; a damaged slot, another vault's slot and a missing Hello key all fall back to the password; turning it on or off needs the right password; a cancelled enrollment leaves no slot and no key; the data key is in neither the stored nor the unwrapped slot bytes.
- `src-tauri/src/quick_unlock.rs`: the same service through the platform crate's `FakeHello`.
- `crates/vaultair-platform/src/windows/dpapi.rs`: a real DPAPI round trip, bound to its entropy, refusing changed bytes. `hello.rs` has a real-Hello determinism test, ignored because it needs someone to approve the prompts (`cargo test -p vaultair-platform -- --ignored real_hello`).
- `src/features/lock/LockScreen.test.tsx`, `src/features/settings/quickUnlock.test.tsx`: the lock screen falls back to the password on cancel and shows only the password when a rule requires it; Settings turns it on and off with the password and warns when there is no TPM.
- `src/features/shell/HelloOffer.test.tsx`, and the `enable_after_password` tests in `service/quick_unlock.rs`: the offer turns it on with one Hello prompt only while the master password is fresh (5 minutes), never in a session Hello opened or a locked one, and falls back to the password dialog otherwise.
- **Hello offer, running app (owner, 2026-10-07, after [PR #23](https://github.com/bubb4rd/vaultair/pull/23)):** the corner card after a master-password unlock; **Turn on** with one Hello prompt while the password is fresh; **Not now** and **Don't ask again**; password dialog when stale or after a Hello unlock; no offer on the demo vault.

Phase 16 (the secret-flow audit) added:
- `src-tauri/src/ipc.rs`: every command and its return type match the reviewed list in `ipc-surface.snap` (109 commands; the count is exact, and a command the test can't read fails it). Only `secret_reveal`, `totp_current_code` and the two generator commands return one of the three response types that carry a secret value, none of those types is embedded in another response, and backup codes, keys, the header and the Hello slot have no TypeScript type. Every command, including those that return no `Result`, has a permission. These tests generate the bindings afresh into a scratch file and read that, not `bindings.ts`.
- `src-tauri/src/logging.rs`: a panic whose message holds a secret and an email is logged by file and line, with none of the message, through the hook the app really installs; a panic place inside a dependency or the standard library is logged without the build machine's folders or user name; and a Tauri error whose text holds a path with a user name is logged as its kind only.
- `src-tauri/src/commands/vault.rs`, `backup.rs`: the create and restore requests, which carry the master password, print nothing of it (or of their paths) when formatted.
- `crates/vaultair-core/src/domain/account.rs`: the two reveal responses serialize their value and never print it.
- `crates/vaultair-core/tests/search.rs`: search hits, saved views, identities and their overview, contact points, the catalog, game profiles, the whole-vault map, the vault's own facts, its settings and its backup status carry no secret from a canary-filled vault. With `tests/accounts.rs` (account responses, health, dashboard) and `tests/graph.rs`, that is every response built from a vault's records other than the reveal ones. The remaining responses hold only paths, flags, counts and settings.
- `crates/vaultair-core/tests/accounts.rs`: the canary run now includes the path `totp_current_code` takes, and the captured log is checked for the code it returned (as a token of its own, so six digits inside a timestamp don't count).
- `src/features/accounts/accounts.test.tsx`: a backup code shown in the Backup codes dialog hides itself after the reveal time, like every other revealed value. (Before Phase 16 it stayed until hidden by hand or the dialog closed.) Selecting part of a shown password and copying or cutting it calls `clipboard_copy_secret` and stops the webview's own copy; dragging it is stopped; a selection that runs past the secret copies nothing; other text copies normally. The setup key, recovery steps, backup codes, TOTP code and generator output use the same hook and are not tested one by one, and none of this has been tried in the real WebView2 window, only in the test DOM.

Not covered by an automated test, and relied on from reading the code or from a manual check: the clipboard exclusion formats on the real clipboard and real Windows Hello (ignored tests, run by hand); capture protection's effect and the Windows session and power events (OS calls behind a trait, faked in tests); that SQLCipher encrypts the rollback journal; that memory is actually wiped; and the log lines of the command layer in `src-tauri`, which the log canary doesn't run (they pass only fixed strings and the fixed-text error types, by construction).
