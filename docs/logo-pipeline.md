# Logo pipeline: implementation guidelines

Guidelines for the agent implementing logo coverage for built-in platforms and games. This is the "manifest-first, fallback-first" approach chosen over a full asset-management system with a review app, a queue and scheduled discovery jobs. Read the whole document before starting; the constraints in the first section are not negotiable.

## Constraints

- **Developer-side only.** Sourcing, review and approval happen in the repo. Nothing about the pipeline ships in the app or touches a customer's vault.
- **No network at runtime.** The app renders only files bundled at build time. CSP stays `img-src 'self' data:`. Don't add a fetch, a CDN URL, or a network crate (`deny.toml` bans them).
- **No network in the pipeline either.** The scripts read the pinned `simple-icons` package and files on disk. No API keys, no provider calls, no `.env` secrets. Candidate files are found by a human and dropped in by hand.
- **Humans approve, scripts check.** A script may report gaps and suggest Simple Icons slugs. It never approves, never replaces an approved file, and never picks "the best match" on its own.
- **Licensing beats coverage.** An entity with no legally usable logo gets a brand-coloured monogram and a recorded reason. That is a finished state, not a failure.
- **No migrations, no vault changes.** The vault's `icon` column, `seed_builtins` and `CATALOG_SEEDS` stay as they are.

## Why the lookup has to change

Today a logo is found by the `icon` slug stored on each platform and game row in the customer's vault (`repo/catalog.rs`, `seed_builtins`). The seed is `INSERT OR IGNORE`, so a slug added to `default_catalog.json` later never reaches an existing vault. Adding a logo next month would only help new vaults.

The fix is to resolve logos in the frontend by the **stable catalog ID** (`builtin-game-overwatch2`), from a manifest bundled with the app. The stored slug becomes a legacy fallback. Every vault picks up new logos on the next app update with no migration.

## Layout

| Path | What | Committed |
|---|---|---|
| `crates/vaultair-core/catalog/logos.json` | The manifest: one record per built-in catalog ID | Yes |
| `src/assets/logos/platforms/`, `src/assets/logos/games/` | Approved logo files, named by catalog ID without the `builtin-pl-` / `builtin-game-` prefix (`games/overwatch2.svg`) | Yes |
| `src/features/catalog/logos.generated.ts` | Generated by `logos:build`; never edit by hand | Yes |
| `scripts/logos.mjs` | The pipeline script (`report`, `suggest`, `sheet`, `build`) | Yes |
| `scripts/logos.test.mjs` | Validation of the manifest and the file rules, run by vitest | Yes |
| `.asset-work/` | Contact sheet and scratch candidates | No (add to `.gitignore`) |

The manifest sits beside `default_catalog.json` so both are "catalog data" and the coverage test can read them together, the same way `catalog.test.tsx` already reads the seed with `import.meta.glob`.

## Manifest format

`logos.json` is an object keyed by catalog ID. Every built-in platform and game in `default_catalog.json` must have exactly one record; there is no "unknown" state.

```json
{
  "builtin-game-valorant": { "kind": "simple-icons", "slug": "valorant" },
  "builtin-pl-xbox": {
    "kind": "monogram",
    "color": "107C10",
    "reason": "Removed from Simple Icons at Microsoft's request; Xbox brand guidelines don't allow use in third-party apps.",
    "checkedAt": "2026-10-06"
  },
  "builtin-pl-example": {
    "kind": "file",
    "path": "platforms/example.svg",
    "color": "1A73E8",
    "source": "https://example.com/press",
    "licence": "Press kit terms allow use of the logo to identify the service.",
    "reviewedBy": "owner",
    "reviewedAt": "2026-10-06",
    "sha256": "…"
  }
}
```

| Kind | Required fields | Optional | Meaning |
|---|---|---|---|
| `simple-icons` | `slug` | `color` (overrides the package hex) | A mark from the pinned `simple-icons` package (CC0), drawn inline as today |
| `file` | `path`, `source`, `licence`, `reviewedBy`, `reviewedAt`, `sha256` | `color` | An approved SVG or PNG under `src/assets/logos/` |
| `monogram` | `reason`, `checkedAt` | `color` | Deliberately no logo; initials in a tinted tile |

Rules:

- `color` is a 6-digit hex without `#`, matching the Simple Icons convention `logoColor` already takes.
- `path` is relative to `src/assets/logos/` and must stay inside it.
- `sha256` is the lowercase hex hash of the committed file. `logos:build` fills it; validation checks it.
- `reviewedBy` is set only by the owner. **An agent must never fill `reviewedBy` for a `file` record.** An agent may prepare a `file` record with every other field, and validation fails until the owner signs it.
- Keep keys sorted by ID, two-space indent, trailing newline, so diffs stay small. `logos:build` rewrites the file in this form.

## Resolution order

`logoFor` in `src/features/catalog/logos.ts` resolves a mark in this order and returns the first hit:

1. (Phase 4, not now) A customer's custom image for this entity, stored in the vault.
2. The manifest record for the catalog ID.
3. The legacy `icon` slug, looked up in the generated Simple Icons map. Keeps any row whose slug isn't covered by an ID.
4. A neutral monogram (today's look).

Return a discriminated union so callers don't guess:

```ts
type Mark =
  | { kind: "path"; slug: string; path: string; hex: string }
  | { kind: "file"; src: string }
  | { kind: "monogram"; color: string | null };
```

Keep `logoColor`, `monogram`, `luminance` and `emailProvider` in `logos.ts`. Remove the hand-written `LOGOS` map and its imports; they move into `logos.generated.ts`.

Email providers: drop the duplicated `icon` field from `EMAIL_PROVIDERS` and resolve the provider's mark through its `platformId`, so a logo approved for a mail platform shows on suggested mailboxes too. Update the "email providers" test accordingly.

## Rendering

- `simple-icons`: unchanged. Inline `<svg viewBox="0 0 24 24"><path d=…/></svg>`, colour from `logoColor` (brand hex if it reaches 3:1 on `--card`, otherwise `currentColor`).
- `file`: `<img src={url} alt="" draggable={false}>` sized to the same glyph box as the SVG. Never inline a file's SVG markup into the DOM, never `dangerouslySetInnerHTML`. Import files through Vite in the generated module (`import overwatch2 from "@/assets/logos/games/overwatch2.svg"`) so they're hashed into `dist`; small files may be inlined as `data:` URLs, which the CSP allows.
- `monogram` with `color`: the same tile and initials as today, with the tile tinted by the brand colour (a low-alpha fill and border mixed into `--card`). The initials use the brand colour when `logoColor` passes 3:1, otherwise the foreground colour. Without `color`, keep today's neutral tile.
- Every mark stays decorative (`aria-hidden="true"`); the name is always written next to it.
- `data-logo` keeps working for tests: the slug, `file:<id>`, or `monogram`.

Add a short rule to `docs/design-system.md` under the node and catalog sections: brand tints appear only on the logo tile, never on text, rows or status, so they can't be mistaken for status or identity colours.

| Call site | ID source |
|---|---|
| `AccountLogo` / `accountMark` (account table, cards, compact rows, detail page, command palette, catalog page) | `platformId` / `gameId` on `AccountSummary` (already in `bindings.ts`). `accountMark` returns `{ id, icon, name }`; its "prefer whichever has a logo" check uses the new resolver |
| `GameProfilesSection`, `CatalogPage` profile rows | `gameId` on `GameProfileView` |
| `CatalogPage` platform and game entries | `entry.id` |
| Graph `NodeMark`, platform and game nodes | `node.recordId` is the catalog ID |
| Graph `NodeMark`, account nodes | **Not available today.** `GraphNode` only carries the account's mark slug. Add `mark_id: Option<String>` to `GraphNode` (`crates/vaultair-core/src/domain/graph.rs`), set in `graph/builder.rs` from the same platform/game choice that sets `icon`, regenerate `src/ipc/bindings.ts` with `cargo test -p vaultair`, and update the graph tests |
| Graph `NodeMark`, prospective accounts | `emailProvider(label).platformId` |

The graph files have uncommitted in-progress work (V8 prospects). Do the graph change last, after that work lands, and don't reformat or restructure the graph files beyond the field.

## The script

`scripts/logos.mjs` is plain Node ESM with no new dependencies, in the style of `scripts/check-release-config.mjs`: small functions, clear error lines, a non-zero exit on failure. Add to `package.json`:

```json
"logos:report": "node scripts/logos.mjs report",
"logos:suggest": "node scripts/logos.mjs suggest",
"logos:sheet": "node scripts/logos.mjs sheet",
"logos:build": "node scripts/logos.mjs build"
```

| Command | Responsibility | Writes |
|---|---|---|
| `report` | Lists built-in IDs with no manifest record, records for IDs that don't exist, `file` records whose file is missing, mismatched or unsigned, and `monogram` records whose `checkedAt` is over 6 months old. Prints counts by kind. Exits 1 only for the first three problems; stale monograms are informational | Nothing |
| `suggest` | For each `monogram` record and missing ID, looks for a Simple Icons slug in the pinned package by name, title and aliases (exact and normalised match only, no fuzzy ranking). Prints candidates with the package's `guidelines`/`license` fields when present, as a reminder to check them | Nothing |
| `sheet` | Writes `.asset-work/sheet.html`: every mark at 24, 48 and 128 px on the dark `--card` surface and on white, with kind, source and licence beside it. Self-contained HTML, images as `data:` URLs, opened by hand in a browser. This is the review UI | `.asset-work/` only |
| `build` | Validates the manifest, computes `sha256` for `file` records, rewrites `logos.json` in canonical form, and generates `logos.generated.ts`: the Simple Icons imports actually used (by manifest slug and legacy slug), the file imports, and a typed `MANIFEST` keyed by ID | `logos.json`, `logos.generated.ts` |

`build` must be deterministic: same inputs, byte-identical output, sorted keys, no timestamps. The generated file starts with a header comment saying it's generated and which command regenerates it.

Only the slugs the manifest names get imported, so the rest of Simple Icons stays out of the bundle, as today.

## File rules

Enforced by validation:

- SVG preferred; PNG allowed when the owner provides only raster. No JPEG, WebP or GIF.
- SVG: under 16 KB, a `viewBox`, square or near-square (aspect ratio within 0.8–1.25). Reject `<script>`, `<foreignObject>`, `<image>`, `<style>` with `@import` or `url(`, any `on*` attribute, any `href`/`xlink:href` not starting with `#`, and `<!ENTITY`/`<!DOCTYPE`. Validation rejects; it doesn't silently clean. Clean the file by hand (or with a one-off tool outside the repo) and commit the clean version.
- PNG: under 32 KB, square, 128 or 256 px, with transparency where the mark has no background.
- The mark must read at 24 px on the dark surface. Check this on the contact sheet, not by eye in the editor.

## Validation

Validation is a vitest suite (CI already runs `npm test -- --run`). The manifest and file checks are in `scripts/logos.test.mjs`, beside the script whose `checkManifest` they call: plain JS, because they read files with Node and the app's tsconfig deliberately has no Node types. The resolver tests are in `src/features/catalog/logos.test.ts`, the rendering tests in `CatalogLogo.test.tsx`, and the `accountMark` and email-provider tests stay in `catalog.test.tsx`. Together they check:

- Every built-in ID in `default_catalog.json` has exactly one manifest record, and every record's ID exists.
- Each record has the fields its kind requires and no unknown fields; colours are valid hex.
- Every `simple-icons` slug exists in the generated map.
- Every `file` exists, stays under `src/assets/logos/`, matches its `sha256`, passes the file rules, and has `reviewedBy`.
- No two records point at the same file. This follows from the naming rule: a record's `path` must be its own ID's file (`games/overwatch2.svg` for `builtin-game-overwatch2`), so another entity's file is rejected.
- `logos.generated.ts` is current: add a CI step after tests, `npm run logos:build` then `git diff --exit-code -- src/features/catalog/logos.generated.ts crates/vaultair-core/catalog/logos.json`, mirroring the existing stale-bindings check.
- Resolver unit tests: ID beats legacy slug; legacy slug still resolves; unknown ID and slug fall back to a neutral monogram; a monogram record carries its colour; `accountMark` still prefers game for game accounts and whichever side has a real logo.
- Rendering tests: a `file` mark renders an `<img>` with empty `alt`, never inline SVG markup; a tinted monogram keeps `aria-hidden`.

Run before every commit:

```bash
npm run logos:build
npm run logos:report
npm run lint
npm run typecheck
npm test -- --run
```

Plus, after the graph change: `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, `cargo test --workspace --locked`, and confirm `src/ipc/bindings.ts` was regenerated.

## Sourcing and approval

What counts as a usable source, in order:

1. **Simple Icons** (the pinned `simple-icons` package). CC0 for the SVG, but the marks remain trademarks and some entries carry brand guidelines. Use for identifying the service only, which is what the app does.
2. **The owner's official brand or press kit**, when its terms allow showing the logo to identify the service in third-party software. Record the page URL and quote or paraphrase the relevant term in `licence`.
3. Nothing else. If neither applies, the record is a `monogram` with the reason.

Never use: SteamGridDB or any community artwork site, fan art, scraped favicons or store-page images, screenshots, AI-generated or hand-redrawn imitations of a logo, or game key art. "It's on the internet" and "everyone uses it" are not licences.

Expect most of today's 19 gaps to end as monograms. Xbox, Microsoft, Outlook.com, Yahoo Mail, AOL Mail, Fastmail and Yandex Mail were removed from Simple Icons at their owners' request, which is a strong signal; the 11 games without logos are owned by large publishers whose terms usually restrict use. Record that honestly rather than working around it.

Approval procedure for a `file` record:

1. The owner (or the agent, as a proposal) finds the source and saves the file under `src/assets/logos/`.
2. Fill the record except `reviewedBy`; run `npm run logos:build` and `npm run logos:sheet`.
3. The owner checks the sheet at 24/48/128 px on both backgrounds, reads the source's terms, and sets `reviewedBy` and `reviewedAt`.
4. Commit the file, manifest and generated module together. The PR diff (GitHub renders image diffs) is the review of record.

Replacing an approved file follows the same procedure. Nothing replaces an approved file automatically.

## Don'ts

- Don't add a database, a local server, a second Vite app, or a queue file. If the entity count outgrows this (several hundred), raise it with the owner first.
- Don't add `.env` handling or provider credentials.
- Don't change `default_catalog.json` IDs; they're the join key for every vault.
- Don't put logo data in the vault or in IPC payloads beyond the `mark_id` field.
- Don't weaken the CSP or the `deny.toml` network bans.
- Don't approve on the owner's behalf.
